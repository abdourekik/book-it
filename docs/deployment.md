# Deploying Book-it

Three pieces, deployed in this order: **database → API → frontend**. Each one needs the
previous one's URL, so the order is not optional.

Everything below has to be done by you — it needs accounts, billing details, and
credentials. Nothing here should ever be committed.

---

## Before you start

- [ ] The repo is pushed to GitHub and CI is green
- [ ] `docker compose down` locally, so you are not confusing local and production data
- [ ] Decide the production URL you want (a `.vercel.app` subdomain is fine to launch with)

---

## 1. Database — Supabase or Neon

Either works. Both give a free Postgres with a connection string.

1. Create a project. Choose a region close to your users, not to you.
2. Copy the **connection string**. It looks like:
   ```
   postgresql://user:password@host:5432/dbname
   ```
3. **Change the scheme to match our driver**, or the app will not start:
   ```
   postgresql+psycopg://user:password@host:5432/dbname
   ```
4. If the provider offers a **pooled** connection string (Supabase calls it the
   transaction pooler, usually port 6543), use it for `DATABASE_URL`. A free web service
   with a small connection limit will exhaust direct connections quickly.

> **Migrations need a direct connection.** Some poolers do not support the statement
> types Alembic emits. If `alembic upgrade head` fails against the pooled URL, run
> migrations once from your laptop against the direct URL instead:
>
> ```bash
> set DATABASE_URL=postgresql+psycopg://...direct-url...
> alembic upgrade head
> ```

Keep the password somewhere safe — a password manager, not a text file in the repo.

## 2. API — Render

The repo has a [`render.yaml`](../render.yaml) blueprint that creates both the web
service and the hourly reminder job.

1. Render → **New → Blueprint**, point it at your GitHub repo.
2. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the `postgresql+psycopg://…` string from step 1 |
   | `RESEND_API_KEY` | from Resend (step 4) — leave blank for now |
   | `APP_BASE_URL` | the Vercel URL from step 3 — leave blank for now |
   | `EMAIL_FROM` | `Book-it <onboarding@resend.dev>` to start |

   `SECRET_KEY` is generated by Render. Do not set it yourself, and do not reuse your
   local one.

3. Deploy. The `preDeployCommand` runs `alembic upgrade head`, so the schema is created
   on first deploy.
4. Check `https://your-api.onrender.com/health` returns `{"status":"ok"}`.

> The free plan sleeps after inactivity. The first request after a sleep takes ~30
> seconds. That is worth knowing before you demo it to anyone.

---

## 3. Frontend — Vercel

1. Vercel → **Add New → Project**, import the repo.
2. Set **Root Directory** to `frontend`. Vercel detects Next.js from there.
3. Add one environment variable:

   | Variable | Value |
   |---|---|
   | `API_BASE_URL` | `https://your-api.onrender.com` |

   Note there is no `NEXT_PUBLIC_` prefix, and that is deliberate: the frontend calls
   the API from the server, so the address is never sent to the browser.

4. Deploy, then copy the resulting URL.

### Close the loop

Go back to Render and set **`APP_BASE_URL`** to the Vercel URL, then redeploy the API.
Until you do, the links inside confirmation emails will point at `localhost:3000`.

---

## 4. Email — Resend

1. Create a Resend account and an API key.
2. Set `RESEND_API_KEY` on **both** Render services — the web service sends
   confirmations and cancellations, the cron job sends reminders. Missing it on the cron
   means reminders silently log instead of sending.
3. To send from your own domain, add it in Resend and set the DNS records they show you.
   Until then `onboarding@resend.dev` works for testing but will land in spam for real
   recipients.

Without a key, the app logs emails instead of sending them and everything else keeps
working. That is the intended fallback, not a failure.

---

## 5. Custom domain (optional)

1. Buy a domain.
2. Vercel → Project → Settings → Domains → add it, and set the DNS records Vercel shows.
3. Update `APP_BASE_URL` on Render to the new domain and redeploy.

## Smoke test

Do this on a phone, on mobile data, not on your laptop. It catches things localhost
never will.

- [ ] The public booking page loads at `/b/your-slug`
- [ ] Slots appear for a future date
- [ ] Booking as a guest succeeds and lands on the confirmation page
- [ ] The confirmation email arrives, and its link opens the right booking
- [ ] The time in the email matches the time shown on the page
- [ ] Cancelling works, and the slot reappears in the list
- [ ] Sign up, sign in, sign out
- [ ] The owner dashboard shows the booking you just made
- [ ] A second browser cannot reach `/dashboard` without signing in

## When something breaks

| Symptom | Likely cause |
|---|---|
| API will not start, `Field required: database_url` | `DATABASE_URL` is missing or has the wrong scheme (`postgresql+psycopg://`) |
| `password authentication failed` | Wrong password — or you are pointed at a different database than you think |
| 500 on every request | Check Render logs. Usually a missing environment variable |
| Emails never arrive | `RESEND_API_KEY` not set on that specific service, or the from-address domain is unverified |
| Email links point at localhost | `APP_BASE_URL` still unset on Render |
| Slots are an hour out | The business timezone is wrong — check it in Settings, not in the code |
| First request takes 30 seconds | Free plan cold start. Expected |

Render logs: Dashboard → the service → **Logs**. Vercel logs: Project → **Deployments** →
the deployment → **Functions**.

---

## Rules that do not bend

- **Never commit a real secret.** `.env` is gitignored; keep it that way.
- **Never reuse your local `SECRET_KEY` in production.** Anyone who has seen your
  local one could mint a token for any user.
- **Rotate immediately if a key is ever committed.** Deleting the commit is not enough —
  it is in the history, and in every clone.
